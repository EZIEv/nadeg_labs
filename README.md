# NADEG

Веб-приложение для расчёта безотказности систем, подбора резервирования, оценки трудоёмкости технического обслуживания и качественного анализа живучести авиационной техники.

Исходные данные задаются пользователем. Три модуля доступны в одном интерфейсе на русском языке. Регистрация не требуется; черновики сохраняются в браузере, а проекты можно переносить между устройствами через JSON.

## Возможности

| Модуль | Назначение | Результат |
| --- | --- | --- |
| ЛР1 | Анализ структуры И/ИЛИ и подбор поэлементного резервирования | Вероятности P и Q, масса, влияние элементов, распределение резервов и диаграмма |
| ЛР2 | Расчёт по условиям эксплуатации и редактируемому регламенту ТО | Количество обслуживаний, суммарная и удельная трудоёмкость, вклады форм и операций |
| ЛР3 | Проверка подготовленного анализа с помощью ИИ | Замечания к отдельным полям, основания, допущения и вопросы к отсутствующим данным |

Варианты из методички используются для проверки расчётов. Программа позволяет работать с собственными системами и параметрами.

## Быстрый запуск через Docker

Понадобятся Docker Engine и Docker Compose с поддержкой `docker compose`. Команды выполняются из корня проекта.

Для первого запуска подготовьте файл настроек:

```bash
cp .env.example .env
```

Чтобы подключить проверку ИИ, заполните `OPENROUTER_API_KEY` в `.env`. С пустым ключом расчёты ЛР1 и ЛР2, ручное заполнение ЛР3, сохранение проектов и экспорт продолжают работать.

Соберите и запустите приложение:

```bash
docker compose up -d --build --wait --wait-timeout 120
```

Откройте [http://localhost/](http://localhost/). По умолчанию приложение публикуется на порту **80** хоста; внутри контейнера используется порт **8000**.

Проверить состояние:

```bash
docker compose ps
curl -fsS http://127.0.0.1/health
```

Ожидаемый ответ `/health`:

```json
{"status":"ok"}
```

Этот запрос проверяет доступность приложения и не обращается к сервису ИИ.

### Порт и автозапуск

Адрес публикации и порт задаются в `.env`:

```dotenv
NADEG_BIND_IP=127.0.0.1
NADEG_PORT=8080
```

После изменения выполните `docker compose up -d`. В этом примере сайт будет доступен только на самом хосте по адресу [http://127.0.0.1:8080/](http://127.0.0.1:8080/). По умолчанию используются `0.0.0.0` и порт `80`.

В Compose настроена политика `restart: always`. На Linux с systemd для запуска Docker после перезагрузки сервера выполните:

```bash
sudo systemctl enable --now docker
```

Docker запускает существующий контейнер без повторной сборки образа. Неуспешный healthcheck сам по себе не перезапускает работающий процесс.

### Обновление и остановка

```bash
# Пересобрать приложение и применить изменения
docker compose up -d --build --wait --wait-timeout 120

# Посмотреть логи
docker compose logs --tail=100 web

# Применить новые значения из .env без пересборки образа
docker compose up -d --no-build --force-recreate --wait --wait-timeout 120

# Остановить приложение и удалить контейнер
docker compose down
```

Изменение `.env` требует пересоздания контейнера: `docker compose restart` не обновляет переданные ему переменные окружения.

## Работа с приложением

1. Выберите вкладку нужной ЛР.
2. Введите исходные данные или откройте JSON через меню «Проект».
3. Пройдите этапы ввода и выполните расчёт либо проверку анализа.
4. Изучите результат, предупреждения и принятые допущения.
5. Сохраните JSON для продолжения работы и скачайте отчёт.

| Формат | ЛР1 | ЛР2 | ЛР3 |
| --- | --- | --- | --- |
| JSON | Редактируемый проект | Редактируемый проект | Проект с материалами и сохранённой проверкой, если она выполнена |
| PDF | Расчёт и диаграмма | Расчёт и таблицы | Текущая аналитическая часть |
| CSV | Таблица элементов и результаты | Регламент и результаты | Аналитическая таблица и материалы в текстовом виде |
| SVG | Диаграмма безотказной работы | Нет | Нет |

Для каждой ЛР сохраняется отдельный текущий черновик. Хранилище привязано к браузеру и адресу сайта, включая протокол и порт. Для переноса на другое устройство или новый адрес предварительно скачайте JSON. Серверная база пользовательских проектов не предусмотрена.

## ЛР1 Безотказность и резервирование

### Анализ системы

Задайте время работы, масштаб параметров отказов и таблицу физических элементов. Структура собирается из групп И/ИЛИ или вводится выражением:

```text
A & (B | C)
```

Система работает, если исправен A и исправен хотя бы один из B или C. Поддерживаются `И`, `ИЛИ`, `AND`, `OR`, `&`, `|` и скобки. Операция И имеет приоритет над ИЛИ.

Повтор ID обозначает один общий физический элемент. Например, `(F & A) | (F & B)` учитывает F один раз при расчёте вероятности и массы. Самостоятельным элементам нужны разные ID.

Принцип расчёта:

```text
qᵢ ≈ ωᵢ × τ
Qᵢ = qᵢ^(kᵢ + 1)
Pᵢ = 1 − Qᵢ
```

Здесь `ωᵢ` учитывает выбранный масштаб, `τ` задаётся в часах, а `kᵢ` означает число дополнительных одинаковых копий. Для группы с одним резервом `kᵢ = 1`, всего в ней две копии.

Логическое условие преобразуется в диаграмму решений по состояниям физических групп. Вероятность вычисляется через случаи исправности и отказа каждой группы, с учётом общих элементов. Отдельно определяется влияние группы: насколько вырастет P системы, если сделать её безотказной.

### Подбор резервирования

Подбор выполняется для последовательной системы без повторов ID:

```text
P ≈ 1 − Σ(ωᵢ × τ)^(kᵢ + 1) ≥ Pзад
M = Σmᵢ × (kᵢ + 1) → min
```

Текущие резервы служат нижними границами поиска. Максимумы, разрешение добавления копий и необязательный предел общей массы задаются отдельно.

Сначала программа пытается найти допустимый вариант, последовательно выбирая добавление с наибольшим уменьшением Q на килограмм. Затем проверяет сочетания в порядке возрастания массы и исключает варианты, которые не могут улучшить результат.

| Статус | Значение |
| --- | --- |
| Минимальная масса подтверждена | Минимум найден в заданных границах резервирования |
| Найдено допустимое решение | Требования выполнены, минимум ещё не подтверждён |
| В заданных пределах решения нет | Ограничения не позволяют получить подходящую структуру |
| Поиск остановлен по лимиту | Отсутствие решения не доказано |

Доступно до 40 элементов; число резервов для элемента ограничено 12. Поиск ограничен выбранным числом структур и временем до 5 секунд. Одновременно выполняются не более двух подборов. Новая топология системы не синтезируется: дополнительные копии добавляются к заданным элементам.

Оба режима используют приближение `qᵢ ≈ ωᵢτ`. Требуется `0 ≤ ωᵢτ ≤ 1`; при значениях выше `0,01` выводится предупреждение о точности. Разные физические элементы считаются независимыми и невосстанавливаемыми, резервы нагружены и одинаковы с основным элементом, переключение идеально.

Таблицу элементов можно импортировать из CSV:

```csv
id;name;rate;mass;reserves;max_reserves;reservable
A;Насос;0,93;0,25;0;3;true
B;Привод;1,13;0,85;0;2;true
```

Обязательные столбцы: `rate` и `mass`. После импорта проверьте время и масштаб параметров отказов.

## ЛР2 Трудоёмкость технического обслуживания

Модуль рассчитывает трудоёмкость по ресурсу до первого ремонта, среднему времени полёта, числу полётов в день и таблице норм ТО. Регламент можно редактировать вручную, импортировать из CSV или вставить из Excel.

Нормы задаются в **чел·ч за одно обслуживание**. Пустая ячейка считается нулём. Старшая периодическая форма должна содержать полный объём выполняемых в ней работ, включая работы младших форм.

Расчёт выполняется последовательно:

1. По среднему режиму определяются лётные дни и количества оперативных подготовок.
2. Для каждого периода `pⱼ` вычисляется число сроков строго до ремонта: `Cⱼ = ceil(t₁ / pⱼ) − 1`.
3. Из числа сроков младшей формы вычитаются совпадающие сроки старшей. В момент первого ремонта периодическое обслуживание не учитывается.
4. Нормы операций суммируются по формам и умножаются на количества обслуживаний.
5. Рассчитываются общая трудоёмкость `Tпл`, удельная `K = Tпл / t₁` и вклады форм и отдельных операций.

Промежуточные вычисления выполняются с точными дробями; округление применяется при выводе. Например, для ресурса 800 ч и периодов 50, 100 и 200 ч получаются соответственно 8, 4 и 3 самостоятельных обслуживания.

Поддерживаются до 100 операций и 8 периодических форм. Периоды должны возрастать; каждый следующий должен быть кратен предыдущему. Эскизы и выбор конструктивных мероприятий по снижению трудоёмкости выполняются отдельно.

## ЛР3 Качественный анализ живучести

На входе: назначение, устройство и размещение объекта, текстовые материалы, изображения и собственный анализ в виде цепочек:

```text
Условие воздействия → Недостаток → Последствие → Мероприятие → Обоснование
```

После команды «Проверить анализ» ИИ оценивает полноту и логику рассуждений, предлагает редакции и указывает недостающие сведения. Замечания привязываются к конкретным полям. Для каждого совета показываются основание, допущения и способ проверки.

Программа сверяет ссылки и дословные цитаты с переданными материалами. Если замечания есть и остаётся время, дополнительное обращение к ИИ проверяет согласованность совета и его основания. Спорные редакции требуют самостоятельной проверки. Кнопка «Принять правку» доступна только при выполнении условий проверки; её нажатие изменяет одно поле.

Цитата подтверждает наличие текста в источнике, но не истинность вывода. Интерпретация изображения остаётся гипотезой. Проверка ИИ также может ошибаться. Для объектов военной авиации помощник ограничивается проверкой полноты, логики и связи с источниками.

В PDF и CSV входят текущий анализ и уже внесённые правки. Непринятые предложения сохраняются в проверке JSON. Изображения хранятся в проекте; в PDF перечисляются соответствующие материалы, сами изображения в него не вставляются. Числовой показатель живучести и эскизы модуль не рассчитывает и не строит.

Ограничения: до 20 строк анализа, 8 материалов и 4 изображений PNG/JPEG. Каждое изображение не должно превышать 2 МБ и 4 млн пикселей, общий объём изображений ограничен примерно 6 МБ. Перед загрузкой браузер уменьшает изображения.

## Подключение ИИ через OpenRouter

Ключ и модель задаются в окружении сервера. Интерфейс не предлагает выбирать провайдера или передавать собственный ключ.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `OPENROUTER_API_KEY` | Пусто | Ключ OpenRouter; без него проверка ИИ отключена |
| `OPENROUTER_MODEL` | `openai/gpt-6-luna` | ID модели для текста и изображений |
| `OPENROUTER_RESPONSE_FORMAT` | `json_schema` | `json_schema`, `json_object` или `prompt` |
| `OPENROUTER_MAX_TOKENS` | `6000` | Максимум токенов ответа одного обращения, от 500 до 16000 |
| `OPENROUTER_TIMEOUT` | `120` | Общий таймаут проверки в секундах, от 10 до 180 |
| `NADEG_AI_PER_IP_HOUR` | `6` | Проверок за скользящий час на IP, от 1 до 100 |
| `NADEG_AI_TOTAL_HOUR` | `30` | Проверок за скользящий час суммарно, от 1 до 1000 |

Модель должна принимать изображения и поддерживать выбранный формат ответа. Чтобы сменить её в Docker, измените `OPENROUTER_MODEL` в `.env` и пересоздайте контейнер без пересборки образа.

Одна проверка анализа включает до двух оплачиваемых обращений: подготовку замечаний и проверку их оснований. Квоты считают проверки анализа, а не обращения к провайдеру. Материалы передаются сервису ИИ при нажатии «Проверить анализ»; ключ остаётся на сервере.

Одновременно выполняются максимум две проверки ИИ. Очереди нет: при занятости обоих мест новый запрос отклоняется и не расходует почасовую квоту. Принятая попытка учитывается, даже если сервис ИИ затем вернул ошибку. Каждая попытка освобождает место в почасовой квоте через 60 минут; перезапуск приложения сбрасывает счётчики.

### Развёртывание за прокси

Docker-образ по умолчанию запускается с `--no-proxy-headers`. Nginx и Cloudflare Tunnel могут передавать IP посетителя в заголовках, но приложение не использует их для определения адреса клиента. Посетители за одним прокси могут разделять IP-квоту.

Если достаточно общего ограничения, можно задать:

```dotenv
NADEG_AI_PER_IP_HOUR=100
NADEG_AI_TOTAL_HOUR=30
```

Тогда отдельная IP-квота не сработает раньше общей. Оба входа, например Cloudflare и обратный SSH через VPS, могут работать параллельно. Это по-прежнему **30 проверок на весь сайт**, а не каждому посетителю. Значение `0` не отключает квоту и считается ошибкой настройки.

Для учёта исходного IP требуется отдельная настройка доверенных прокси и нормализация заголовков на каждом входе. Счётчики находятся в памяти одного процесса; несколько процессов или экземпляров приложения потребуют общего ограничителя.

## Локальный запуск без Docker

Требуется Python 3.11 или новее. Docker-образ использует Python 3.14. Команды ниже предназначены для Linux/macOS и выполняются из корня проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[dev]'
python -m uvicorn nadeg.main:app --reload --no-proxy-headers
```

Откройте [http://127.0.0.1:8000/](http://127.0.0.1:8000/). В PowerShell окружение активируется командой `.venv\Scripts\Activate.ps1`; установка пакета и запуск Uvicorn выполняются теми же командами `python -m ...`.

При локальном запуске `.env` не загружается автоматически. Если файла ещё нет, создайте его по образцу `.env.example` и заполните ключ. Для подключения ИИ задайте переменные в окружении процесса. В Bash можно загрузить свой заполненный файл перед запуском Uvicorn:

```bash
set -a
source .env
set +a
```

Зафиксированные версии рабочего окружения находятся в [requirements.lock](requirements.lock), производственные зависимости образа в [requirements.runtime.lock](requirements.runtime.lock).

## Тесты

После установки зависимостей разработки:

```bash
python -m pytest -q
```

Тесты проверяют логические структуры с общими элементами, подбор резервов, расчёт трудоёмкости, импорт и экспорт, ошибки ввода и обработку ответов ИИ. Ответы провайдера подменяются: для запуска тестов ключ OpenRouter и оплачиваемые обращения не нужны.

## Структура проекта

```text
nadeg/
  main.py             HTTP API и страницы приложения
  models.py           Входные данные ЛР1
  engine.py           Анализ структуры и подбор резервирования
  boolean.py          Вероятности логических состояний
  diagram.py          Диаграммы ЛР1
  export.py           Отчёты ЛР1
  maintenance.py      Расчёт ЛР2
  maintenance_io.py   Импорт и отчёты ЛР2
  lab3.py             Данные анализа и проверка ссылок
  lab3_ai.py          Обращения к ИИ и проверка оснований
  lab3_io.py          Отчёты ЛР3
  templates/          HTML-страницы
  static/             JavaScript и CSS
  assets/             Шрифты для PDF
tests/                Расчётные и API-проверки
```

Серверная часть написана на Python с FastAPI. Интерфейс использует HTML, CSS и JavaScript без отдельного этапа сборки. PDF формируются через ReportLab, проверка изображений использует Pillow, обращения к ИИ проходят через OpenRouter.

## Примечания к размещению

- `.env` и файлы `*.api` содержат локальные настройки и ключи. Они исключены из Git и Docker-образа; не добавляйте их в публикуемые архивы.
- Контейнер работает без root, с файловой системой только для чтения и временным каталогом `/tmp`. Docker-сокет и каталоги хоста ему не передаются.
- Для публичного сайта настройте HTTPS и ограничения массовых запросов на входном прокси. Почасовые квоты ЛР3 ограничивают число проверок, а не стоимость обращения к выбранной модели.
- Вложенный Docker в LXC может требовать отдельного профиля запуска. Файл [compose.lxc.yaml](compose.lxc.yaml) снимает внутренний AppArmor-профиль Docker только для сервиса NADEG. Используйте его при соответствующей ошибке вложенного Docker; для обычного VPS он не нужен.

Если образ `nadeg:local` уже собран или загружен на LXC-хост, этот вариант запускается так:

```bash
docker compose -f compose.yaml -f compose.lxc.yaml up -d --no-build --wait --wait-timeout 120
```

При последующих обновлениях используйте тот же набор Compose-файлов.
